# Starter-project quality and continuing user work

Status: bounded implementation checkpoint in progress, 2026-10-27. Read the
[checkpoint](entries/2026-10-27_PROFESSIONAL_STARTER_PROJECTS.md) for exact source,
validation, model, publication and live-acceptance evidence. A policy or source
check is not proof that generated applications work or look professional.

## Ownership and scope

The user's requested outcome, chosen stack, style and constraints remain the
acceptance target. Brain owns programming intent and the persistent requirement
contract. The shared delivery-policy owner supplies compact generation guidance
to both conversation and coder engines, including compact repair turns. Existing
Station/artifact owners retain project identity, ownership, revision checks,
source composition and ZIP downloads. This update adds no competing project
store, executor, provider permission or model authority.

For browser application delivery, the starter-quality contract asks the model
to build a usable primary flow and a coherent presentation. It does not mandate
a particular framework, a fixed visual theme, cards, gradients, multiple files,
network service, database or enterprise architecture. An explicitly minimal
example, single-file page, chosen design, existing stack or deliberately narrow
feature set stays authoritative. Activation requires an authored web-page
programming intent; review/explanation, native programs, API/workflow tasks,
missing web-page contracts and explicitly requested scaffolds are excluded.
Internal GitHub JSON subtasks keep their existing output contracts.

Starter software requests must first reach the coding route. Explicit frontend
stacks such as React, Vue and Next.js keep their chosen source/build format rather
than being forced to emit standalone HTML. React Native, Flutter and backend
stacks such as Django retain native/backend ownership; browser-quality defaults
do not silently become requirements for those projects.

`project_quality.project_quality_contract` derives bounded metadata with schema
`swrlz-project-quality-v1`, create/continue work mode, user/existing-project design
authority and an explicit guidance-only verification state.
`project_quality_policy` is consumed by the existing shared
`project_delivery_policy` after application-capability guidance. Normal and compact
repair paths use the same policy seam; no new planner or source store is added.

## Generation contract

For a new application, choose the smallest complete implementation that serves
the user's goal. Deliver actual named source files and every required local
dependency. Connect visible controls to real behavior; include useful empty,
invalid-input and error states when those situations exist. Avoid presenting
unimplemented actions as available features.

Use readable type, consistent spacing, a clear action hierarchy, legible colors,
reachable controls and layouts that adapt to narrow screens. Prefer semantic
controls with accessible names, visible keyboard focus and usable form labels.
These are generation requirements subject to observation, not properties inferred
from the presence of CSS or a few keywords.

Provide truthful, proportionate run instructions. Do not invent a working
backend, authentication, API, deployment, compiler result or successful test.
Local-only data and storage should be identified as such. Complete-source and
no-unrequested-placeholder contracts continue to apply; a requested template
remains a legitimate, explicitly limited deliverable.

Output reservation must reflect an actual multi-file deliverable. An actionable
request naming several source files or a starter software project should receive
the existing project allowance rather than depend on the exact phrase “project
files.” Ordinary/project/large output tiers remain bounded at 4096/8192/16384
tokens within the real 32K context, with compact identity/format/internal-JSON
overrides and complete-source reservation preserved. A larger allowance is not
evidence that the model uses it or completes the requested project.

## Continuation contract

An owned saved project remains the unit of continuation. A feature request must
preserve the original requirements, explicit negative constraints, established
interfaces and unrelated working behavior. Native/script projects need this
intent continuity as well as HTML projects. New instructions may deliberately
change an earlier requirement; they do not silently erase every other one.

Retain the established visual language, components, interaction patterns and
storage/data format unless the user requests a redesign or the requested change
requires a clearly identified adjustment. Inspect the actual supplied source;
do not claim that unselected or unavailable files were read.

Return complete changed or newly required files at their exact saved paths.
The existing revision workspace composes them into the current tree and keeps
omitted files unchanged. Omission does not delete or rename a file. A follow-up
does not create another project unless the user requests one. Stale revisions,
foreign ownership and conflicting file paths retain their existing rejection
rules. See [revision workspace](PROJECT_REVISION_WORKSPACE.md) and
[selected-context/download behavior](PROJECT_REVISION_DOWNLOAD_UI.md).

## Local web dependency evidence

The existing web source validator is extended conservatively to catch declared
local browser assets that are absent from the composed returned project, such
as a linked stylesheet. HTML-relative and stylesheet-relative references must be
resolved against their actual containing file. External resources, data/blob
URLs, fragment references and genuine build-required projects retain their
separate handling; the check neither downloads a dependency nor invents one.

For non-build-required HTML, the bounded graph covers linked stylesheet and icon
assets, image/media/source `src`, video posters, image-input `src`, SVG image
`href`/`xlink:href`, executable local script sources, inline style blocks/attributes,
and literal CSS `url()`/`@import` references in reachable stylesheets. References
use each containing file's parent; query/fragment suffixes and percent-encoded
path segments are normalized, and the first HTML base URL is respected. Shared
stylesheets and cycles are visited once. Missing declared local files report
`missing-project-asset:<path>`.

Comments, CSS content strings and non-executable script data do not create asset
requirements. External/protocol-relative, data/blob and fragment-only references
are not fetched or certified available. Actual declared build-required projects
retain separate build verification. `srcset`, escaped/dynamic CSS URLs and unused,
unreachable stylesheets remain ungraded. This is not a browser, CSS engine,
arbitrary bundler resolver or completeness proof. A source PASS keeps execution
unverified.

## Acceptance and evidence

The bounded engineering benchmark creates a model-authored, responsive taskboard
and continues that same saved project with additional user features. It checks
actual primary interactions and preservation of earlier behavior, not a prepared
expected implementation. Prompts contain requirements only; trusted fixtures and
grader implementation are withheld from the models.

Downloaded model source runs only in the existing Bubblewrap browser evaluator,
without outside network, credentials or host checkout access. Keep the delivered
ZIP bytes unchanged and record its source/member/ZIP hashes. Use independent
desktop, mobile, keyboard, invalid-input, persistence and browser-error evidence
where applicable. Inspect screenshots separately for hierarchy, consistency and
readability. Geometry/visibility heuristics are limited layout baselines, not an
automatic certificate of professional design.

Record each evidence level separately: deterministic source tests; actual model
generation; owned artifact/revision transport; isolated application behavior;
visual inspection; exact-source CI; guarded publication; observed deployed
revision; and actual hosted follow-up. Failures remain part of the record.

This checkpoint does not establish universal coding competence, a complete 3D
editor, autonomous large Android project generation, signed-in provider work,
reliable very long responses, weight training or a larger-model promotion.

## Requirement extraction and project binding

Brain retains ordinary directive clauses such as Start, Save, Persist and Make,
and per-item obligations such as Each task needs a checkbox. A clause containing
both a positive behavior and a negative constraint remains verbatim in both
categories; fenced source cannot supply new requirements. The lists remain
bounded and never mark a behavior executed or passed.

Carrying a prior contract is bound to the selected saved artifact. Switching to
a different pinned project retires unrelated prior language, requirements and
inherited repair state. The selected source, rather than another project's most
recent HTML, supplies its medium. This is not an ownership grant; Station still
validates the selected target and revision.

## Bounded source review for polished starters

Explicitly professional or polished authored web starter requests receive a
bounded model source review after source/completion checks and before code is
delivered. The reviewer compares the complete candidate with numbered canonical
user requirements; it cannot invent requirements, permissions, execution results
or implementation fixtures. Findings stay advisory source observations. Valid
findings use the existing bounded complete-file repair loop; unresolved scoped
reviews are not silently advertised as complete. Ordinary small code examples,
explanations, reviews, internal provider JSON and explicit scaffolds keep their
existing owners.

Owned changed-file responses are reviewed against the composed saved tree so
omitted preserved files cannot look missing. Review context is bounded; a large
project that exceeds the starter review scope keeps ordinary source validation
with an explicit review-not-run observation, rather than silently truncating
canonical source or blocking all selected-file edits. No source review is a
browser/compiler test or independent professional-design acceptance.

Persistent visible form labels, useful empty-list guidance, clear focus and
selection states, wrapping that leaves actions reachable, and coherent visual
hierarchy are explicit quality expectations. They remain subordinate to the
user's chosen style, stack and deliberately minimal scope.

The source audit uses at most two JSON reviews, each with a requirement-sized
allowance bounded at4096tokens, within the existing maximum three code drafts.
JSON grammar and server checks require exact coverage of canonical requirement
IDs with source-only assessments and literal evidence. An empty assessment array
cannot approve a project. Supported positive/preservation requirements need a
nonempty exact source quote; missing, duplicate or inconclusive assessments cause
bounded repair. Superseded/out-of-scope exemptions require a real continuation
and a literal newest-instruction quote. A continuation provides
both previous canonical source and the full composed proposed tree; combined
source admission is bounded at64KiB/32files and the actual context window. The
newest instruction defines edit scope, and review cannot require unrelated old
defects to be repaired. Known unresolved review findings cannot be escaped by
padding a replacement beyond the audit limit. Public metadata records only
bounded status/timing/IDs/hashes, not reviewer prose or execution claims.

Actual candidatee1 review missed source gaps and was not published; see the
[checkpoint](entries/2026-10-27_PROFESSIONAL_STARTER_PROJECTS.md) and its retained
negative evidence. Mandatory assessment coverage is a source protocol repair,
not proof that the model can produce every requested project.
