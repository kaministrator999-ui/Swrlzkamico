# Bounded large code and document generation

Checkpoint: [editor project completion](entries/2026-10-25_EDITOR_PROJECT_COMPLETION.md).
State: source candidate; actual long-form native/hosted behavior is recorded separately.

The owner requested substantially more response room for 700M and substantial code/document projects. Both native model engines now use a bounded 32,768-token runtime context. Shared request policy reserves output before optional history fitting:

| Request | Output allowance |
| --- | ---: |
| Ordinary conversation or code | 4,096 tokens |
| Editor or multi-file project; explicit 1,000–1,999-word response | 8,192 tokens |
| Explicit large/comprehensive code project, long document/report, at least 2,000 words or at least 5 pages | 16,384 tokens |

These are decode allowances, not required output lengths or proof of quality. The current user's concise/brief/small-fix instruction overrides a carried large-project request for prose. A complete-source edit still reserves the actual canonical source token size plus 1,024 tokens of headroom, up to 16,384. Source larger than that complete-delivery bound is rejected explicitly; concise wording cannot starve the full-file delivery. Existing narrow identity, exact-step, internal GitHub plan/candidate and lyric-shape response modes retain their special caps. Incidental mentions of a large topic do not alone request a large output. Long source explanations can use the larger tier instead of the ordinary short verified-file answer path.

Both pinned GGUF metadata headers were read directly, without executing their generated content: LFM2-700M declares `lfm2.context_length=128000`; Qwen2.5-Coder 7B declares `qwen2.context_length=131072`. The runtime 32K window stays below both declarations; this does not establish useful generation at their maximum windows. The existing 32 GiB environment memory bound is unchanged. A larger runtime window can increase KV-cache memory and prompt latency.

The mandatory current request, canonical source under repair, and latest imported source under editing remain intact. Raw imported HTML does not need a stored artifact ID to become mandatory editing context; the application still cannot invent an artifact identity or overwrite an unrelated artifact. If required input plus requested output cannot fit, the engine reports the context limit rather than silently deleting source. Optional history can be removed first. Context telemetry records `responseBudgetTier`, requested output reservation, input size and omitted optional history.

The shared delivery policy requires implemented behavior rather than pseudocode, TODO/empty handlers or comments standing in for code, unless the user explicitly requested a scaffold/pseudocode/placeholders. Large work is not silently abbreviated: if a whole scope exceeds one delivery, the model must identify the completed scope and remaining work. A stage contains complete files or a complete document section. This is a model instruction and source validation boundary, not an automatic multi-stage project executor. The application packages actual persisted files, not promised future files. Automatic code continuation or whole-project completion is not implied. Explicit ordinary-prose word targets have the separate bounded revision behavior below.

Observed model `finish_reason=length` remains an explicit `OUTPUT_TOKEN_LIMIT` failure. A larger response tier cannot turn truncated source into a completed artifact. Existing source gates and independent runtime evaluation remain separate.

## Bounded revision for explicit prose word targets

Both engine loops now use the shared `longform_completion.py` helper for explicit ordinary-prose generation requests between1000 and12000 words. A maximum such as “up to1200 words” is not a minimum target. Code/projects, internal structured GitHub subtasks, identity and exact-format modes, lyrics/poetry, quoted/transformed source, and unsupported word-count-language cases retain their existing owners. This scope is intentionally narrower than all long documents or every substantial request.

The first full draft is buffered and measured using the Unicode lexical counter above. A normally stopped underlength draft can receive one model-authored complete revision, with the full original model messages and unchanged prior draft. Feedback asks for distinct explanation and relevant examples rather than padding and preserves the original topic, constraints and supported facts. The application neither adds prose nor joins draft fragments. Two drafts together share the original bounded output allowance; token observations distinguish provider usage from the visible-text tokenizer plus one stop-token estimate. Mandatory context is never clipped to make a revision fit, and insufficient remaining context/output room stops revision.

Only one whole model draft is published. A normally stopped draft is preferred over a truncated replacement; among eligible drafts the longer one is selected. If the selected draft remains short, the request ends `FAILED` with `LONGFORM_LENGTH_NOT_MET`, rather than `COMPLETED`, and the displayed draft remains incomplete for that request. A length-only PASS requires a normal observed stop and the measured requested minimum. It does not verify factual accuracy, citations, prose quality or broader document completeness; telemetry explicitly says `REQUESTED_LENGTH_ONLY`. Exact word-count and unbounded continuation promises are not introduced.

The helper's8 tests and both engine loops'4 tests cover routing exclusions, complete-context retention, one substantive revision, combined token bounds, no padding, truncated replacements, truthful underlength failure and ordinary/internal-JSON paths. These controlled-draft checks establish implementation behavior only.
