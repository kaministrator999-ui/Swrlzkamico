# 2026-11-05 — §C Image-to-Chat Progress, Local CPU Queue & Recovery (v5)

**Scope:** canonical §C Chat in existing HF Space `kamiloki/Swyrlz`. Source ownership branch `fix/chat-embed-mobile-composer-v1-20261103`. No changes to §E editor, model weights, microphone recognizer, Google sign-in, or paid inference services.

## Owner-observed regression
Two Android Chrome screenshots showed image upload stuck at composer-only `Analyzing image…`; after a roughly two-minute interval the interface showed `Local image analysis is busy. Try again shortly.` with original image still in composer. Previously the image request blocked the browser's normal send until local SmolVLM completed, while `_inference_lock.acquire(blocking=False)` returned an immediate 429 if an earlier CPU inference still held the lock. Image analysis took no visible place in the chat message area.

## Implementation
- `hf_space/chat_vision.py` now accepts a **Google-account-owned in-memory vision job** via POST `/api/lalm_station/vision` (202, jobId). GET `/api/lalm_station/vision/status?jobId=...` returns actual worker phase: QUEUED, PREPROCESSING, LOADING_MODEL, ANALYZING, COMPLETE, or FAILED. Owner identity is reverified on every status read; unauthorized accounts cannot read each other's descriptions or job IDs. Jobs are limited to one executing CPU inference plus one queued job, and completed outcomes expire from bounded process memory. Identical owner+image+question retries reuse the existing job ID/result rather than duplicating expensive inference.
- `hf_space/station.py` returns the verified account ID to the authenticated vision job handler rather than just an auth pass/fail check.
- `chat/§wyrlz/index.html` immediately displays a temporary **image+question progress card in the conversation viewport** with five simple steps: Upload image; Prepare image and load model; Identify visual details; Pass description to §C; Generate chat response. Actual HTTP/server events move steps forward; no fabricated percentage or fictitious completed phases. The card is explicitly not yet an authoritative saved chat message. After vision completes, the unchanged Station `/send` persists the original image-derived text handoff and streams the regular assistant reply. Errors remain visible in the chat area and leave the selected image attached for retry. Browser Stop waiting aborts polling but does **not** claim to terminate a native llama.cpp inference. Switching threads during slow analysis prevents the image from being submitted to an unintended thread.
- `tests/test_chat_vision_v1.py`, `tests/test_chat_media_v1.mjs` updated for asynchronous job lifecycle, one additional queued CPU job, duplicate retries, owner isolation, error sanitation, and inline JS composition.
- Existing v4 `visionAnalysis.descriptionSentToChatModel` export remains unchanged; image pixels are never added to account history. No GPU, paid API token or hardware upgrade.
