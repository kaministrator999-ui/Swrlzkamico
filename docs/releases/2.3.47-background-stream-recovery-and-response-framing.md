# Server Runtime v2.3.47 — Background stream recovery + response framing

## Module state

- Server Runtime: **v2.3.47**
- Web Chat: **v1.4.42**
- LALM Engine: **v2.1.25** (unchanged)

## Triggering evidence

User verification showed three issues:

1. A normal greeting response still printed the assistant name as visible content.
2. A coding response could contain only the code snippet, with no natural lead-in, explanation/overview, or closing line.
3. Backgrounding/leaving the browser during an already-generating response could surface a browser `network error` instead of recovering the pending server-side request when the user returned.

## Root cause of background recovery failure

`chat_background_resume.js` marked the original browser stream request id as live as soon as `fetch()` started. If the browser connection later failed while reading the stream, that request id could remain in the local live set. Recovery then refused to reattach because it believed a live recovery connection already existed. The base Chat sender also marks a transport exception as failed, leaving the visible network error until recovery rewrites the message state.

## Changes

### Background/reconnect behavior

- Original foreground stream requests are no longer inserted into the recovery `live` set.
- Recovery now uses the existing Chat `active` request as the guard against duplicate attachment while the original stream is genuinely active.
- Once the original stream fails or the page returns and `active` is gone, the saved pending request can reattach immediately.
- Recovery clears stale `meta.error` text when it moves the message back into streaming/reconnecting state, so `network error` is not left painted while a retry is underway.
- Visible-page recovery checks now run every 1.5 seconds, and `online`, `focus`, `pageshow`, and `visibilitychange` all trigger an immediate retry attempt.
- Existing request-id replay/restart reconciliation remains: same-prefix regeneration catches up invisibly; divergent regeneration switches to a clean redo rather than concatenating incompatible text.

### Response-shape behavior

- Chat now supplies one stable response directive to the LALM stream request.
- Ordinary responses must not print/announce/sign with the assistant name unless the user explicitly asks about identity/name.
- Programming responses default to a short natural lead-in, complete runnable code, a concise explanation/overview, and a short natural closing sentence unless the user explicitly asks for code only.
- The directive also retains syntax/formula/I/O/code-explanation consistency requirements.
- Added `chat_response_polish.js` as a presentation safety layer. It removes standalone assistant-name lines that still leak into rendered content, supplies a neutral lead-in when a code artifact begins without one, and can move a short final closing paragraph outside the nested code artifact so the response has a natural wrap-up after the container.

## Hosting boundary

The LALM uses detached in-memory jobs on the active server worker. A browser/tab disconnect no longer blocks Chat from retrying the same request. If the original worker survives, the request can replay/continue. If a new instance receives the same request, the browser reconciliation layer compares regenerated output against the saved partial and either continues from the matching prefix or performs a clean redo.

This still does **not** turn Vercel serverless memory into durable infrastructure. A worker may be frozen or destroyed after client disconnect. Strict survival across process destruction would require a durable queue/event store outside worker memory. v2.3.47 therefore guarantees browser-side pending-request recovery behavior, not permanent worker-memory durability.
