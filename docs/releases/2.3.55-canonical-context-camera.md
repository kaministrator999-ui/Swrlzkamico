# Server 2.3.55 — Canonical Context Camera + Identity Separation

**Date:** 2026-09-11  
**Server Runtime:** 2.3.55  
**Web Chat:** 1.4.50  
**LALM Engine:** 2.1.26 unchanged  
**Deployment:** NONE  
**Restart:** NONE

## Why this event exists

Whole-conversation camera evidence showed that same-thread prefill reuse can work (`reused 102`) and then collapse back to `cached 0` on a later turn. The same evidence also showed the model confusing the user's newly supplied name (`Kami`) with the assistant identity when asked `What's your name?`.

A contributing architecture risk is that Chat presentation filters can hide or rewrite visible assistant text while the server-side recurrent/checkpoint state was produced from the model's raw generated stream. Future prompt history must therefore distinguish canonical model output from display-polished text instead of assuming they are always identical.

## What changed

### Canonical context layer

- Added a runtime Chat context layer that runs after the existing request normalizer but before the network request leaves the browser.
- Previous assistant turns now prefer hidden canonical `modelText` when that value is available; visible `text` remains the presentation copy.
- User turns continue to have obsolete intent-marker text removed before they are sent back as history.
- The response directive is stable across turns and explicitly separates assistant identity from user-supplied names:
  - assistant name is `§wyrlz`;
  - a name supplied by the user belongs to the user unless the user explicitly renames the assistant;
  - asking the assistant's name should resolve to `§wyrlz`;
  - ordinary social replies should participate naturally rather than narrating that a greeting occurred.

### Context camera instrumentation

- Added a second runtime layer around stream event consumption.
- Raw assistant DELTA text is captured before display filters modify it.
- On terminal state the assistant message now records hidden canonical model text plus a compact `contextCamera` diagnostic object.
- The existing whole-conversation camera automatically includes these fields because it already exports raw message state.
- Camera diagnostics record:
  - turn intent;
  - history source;
  - history message count;
  - number of assistant history turns using canonical model text;
  - raw assistant character count;
  - visible assistant character count;
  - whether raw and display text differ;
  - whether a leading standalone assistant-name line was filtered.
- A compact `CONTEXT_CAMERA` trail receipt is added at terminal completion so the normal Activity log and exported camera evidence can show the transition without requiring a separate debugging UI.

## Diagnostic purpose

This event intentionally adds observability before making a deeper recurrent-state change. The next camera log should let us distinguish these cases:

1. visible-text filtering caused the history/checkpoint mismatch;
2. raw text and display text are identical but token re-encoding still diverges from the exact generated-token checkpoint;
3. worker replacement removed the prior in-memory checkpoint entirely;
4. the identity directive corrected user-name/assistant-name separation independently of cache behavior.

The goal is to steer future cache changes from receipts rather than guessing and to preserve already-working behavior while isolating the unstable boundary.

## Runtime wiring

`runtime_pages/manifest.json` loads the new layers in this order:

1. `chat_context_canonical.js`
2. `chat_background_resume.js`
3. `chat_context_camera.js`
4. existing response polish

This order is intentional: the canonical request layer sees the fully normalized outbound request, while the camera event layer sees raw stream events before the existing background-resume/display filter consumes them.
