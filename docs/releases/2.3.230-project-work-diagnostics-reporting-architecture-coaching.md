# Server 2.3.230 — Project-work diagnostics, reporting, and architecture coaching

**Overall Server:** `2.3.230`  
**LALM Engine:** `2.1.76` / `v65` unchanged  
**Chat:** `1.5.65` unchanged  
**Affected component versions:** none  
**Deployment / restart:** NONE

## Outcome

The project-development contract was reconciled so future §wyrlz project work has one clear startup router and one owner for each major engineering responsibility.

The event adds four durable behaviors:

1. issue/fix/debug work automatically inspects relevant repository/live diagnostic evidence and adds bounded cameras only when observability is insufficient;
2. substantial project-work responses follow a dedicated readability/truth-state standard;
3. Project Start routes architecture, versioning, diagnostics, deployment, roadmap, and reporting to dedicated canonical documents instead of duplicating their detailed rules;
4. architecture knowledge can be taught and adapted for user-owned projects, including proportional structure and informed simplification/removal of optional architecture.

## Architecture reconciliation

Reviewed the Project Start contract, Hotfix Rules, Version/Module Evolution contract, Architecture Reconciliation Protocol, camera/log runbook, roadmap/release records, Engineering Log, current version authorities, deployment workflow, and the new reporting/coaching requirements.

Found governance overlap rather than runtime feature overlap:

- Project Start had become a large secondary owner of architecture/version/deployment detail;
- Hotfix still labeled itself as first despite Project Start being the canonical entrypoint;
- Version Evolution carried another startup-order definition;
- camera/log guidance was named and framed around Chat even though the diagnostic method applies project-wide;
- no dedicated project-work response/readability owner existed;
- architecture execution existed, but user-facing architecture teaching/adaptation was not yet explicit.

Integration path:

- **Project Start** → router/orchestrator only;
- **Hotfix Rules** → mutation/runtime-main/deployment mechanics;
- **Version Evolution** → Server/module lineage and concurrency;
- **Architecture Reconciliation Protocol** → engineering discovery/integration method;
- **Camera/Logs** → project-wide diagnostic evidence and instrumentation;
- **Response Standard** → project-work conversational reporting;
- **Architecture Coaching Guide** → proportional user-project architecture teaching;
- **Roadmap** → durable progress/release memory.

No new competing runtime owner was introduced.

## Automatic issue-diagnostic rule

When fixing/debugging/investigating/verifying a project defect, §wyrlz now follows this contract automatically:

```text
symptom
→ reconcile architecture owner
→ inspect existing repository evidence
→ inspect accessible live/runtime/workflow logs
→ observability sufficient?
   → yes: diagnose
   → no: add smallest bounded camera at missing boundary
→ reproduce/request
→ inspect evidence
→ fix canonical owner
→ re-check cameras/logs
→ acceptance
```

Default when diagnosis is uncertain: **inspect first → instrument second → mutate third**.

## Response/readability standard

`docs/engineering/SWRLZ_PROJECT_WORK_RESPONSE_STANDARD.md` is now a required Project Start document. It owns:

- readable Markdown structure;
- compact Status / findings / changes / verification / version-deployment / remaining-state reporting;
- source-complete vs static/runtime/live truth states;
- evidence-oriented issue reporting;
- meaningful progress updates without low-level narration spam.

## User architecture coaching

`docs/engineering/SWRLZ_ARCHITECTURE_COACHING_GUIDE.md` teaches §wyrlz to apply the same architectural literacy to user projects without blindly imposing §wyrlz's internal structure.

It includes:

- proportional architecture by project scale;
- plain-language explanations of why boundaries matter;
- teach-while-building behavior;
- distinction between required constraints, strong recommendations, and optional preferences;
- respect for user decisions to simplify optional structure;
- clean migration/removal so rejected architecture does not leave stale duplicate paths;
- architecture checkpoints as a project grows.
