## Symptom

The per-response Activity Log still behaved incorrectly across the live-stream → finalized-response boundary: it could fail to remain visible during generation, lose expansion state, or render inconsistently after the response completed.

## Evidence and root cause

`web/chat_stream_incremental.js` still directly mutates the live `<details class="trace">` surface during streamed repaint, including a hard `details.open = true`. Separately, `web/chat_activity_immediate.js` owns persisted `message.meta.activityExpanded`. That left two mechanisms mutating the same DOM state.

The final response path also replaces the live article with a freshly rendered article. The Activity controller previously only recreated a missing trace for live messages, so a terminal article with retained activity history could still lose the trace if another renderer omitted it.

## Architecture reconciliation

The canonical owner remains `web/chat_activity_immediate.js` at the message/model boundary. Incremental streaming may render or replace response DOM, but Activity expansion truth is `message.meta.activityExpanded`.

This event strengthens that owner without introducing a third state source:

- completed assistant messages with retained `meta.trail` now recreate a missing Activity Log;
- the Activity controller observes transient `open`-attribute mutations and reasserts the persisted model state;
- delegated click/keyboard handling remains valid regardless of which renderer created or replaced the `<details>` node;
- the controller exposes `window.__swrlzActivityController` for future renderer reconciliation instead of requiring duplicate Activity state logic.
