# Server Runtime v2.3.45 — Background generation resume

## Module state

- Server Runtime: **v2.3.45**
- Web Chat: **v1.4.40**
- LALM Engine: **v2.1.25** (unchanged)

## Goal

Allow a submitted local-LALM request to keep progressing independently of the visible Chat page and allow the Chat UI to catch up when the user backgrounds, reloads, leaves, or returns to the page.

## What changed

- Added `web/chat_background_resume.js` as a runtime-owned Chat lifecycle/resume layer.
- Chat records pending stream request metadata, including the original request id, thread id, stream URL, and normalized request body, in browser-local persistent storage for bounded recovery.
- The same request id is reused when Chat reattaches. This allows the replayable detached R39 job on the active server worker to replay already-generated stream events and continue streaming new events.
- Replayed events are sequence-deduplicated before applying them to the message so assistant text is not appended twice.
- When Chat becomes visible again through `pageshow`, focus, or `visibilitychange`, the current thread automatically attempts to reattach to any pending request.
- The assistant message/activity state is updated while reconnecting so the user sees that Chat is catching up rather than treating the request as lost.
- Pending entries are cleared only when Chat observes a terminal `COMPLETED`, `CANCELLED`, or `FAILED` event. Stale browser recovery metadata expires after 30 minutes.
- Page hide/background events persist current Chat state before the browser may suspend JavaScript.
- `runtime_pages/manifest.json` now loads the background-resume bridge after incremental stream rendering and before boot-ready release.

## Existing server/LALM behavior verified

- R39 generation uses detached in-memory jobs keyed by request id and can replay their event history to a later consumer on the same live worker.
- Local generation and progressive prefill/checkpoint work run on the server side rather than depending on DOM rendering or the Chat page remaining foregrounded.
- Browser Chat authorization uses the same-origin HttpOnly server-managed Chat session cookie, so reattachment does not require exposing the permanent Chat secret to browser storage.

## Important durability boundary

This release provides normal background/tab/reload/network-reconnect continuity by combining detached server generation with browser reattachment and event replay. The detached job store is currently worker-memory. If the hosting platform destroys or replaces that worker, its in-memory job disappears. Reusing the same deterministic request id/body provides a recovery attempt on another worker, but a strict guarantee across process loss or deployment replacement requires a durable job queue/event store outside worker memory.
