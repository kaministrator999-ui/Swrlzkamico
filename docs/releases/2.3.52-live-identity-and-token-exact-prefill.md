# Server Runtime 2.3.52 — Live identity suppression + token-exact next-turn checkpoints

Date: 2026-09-11

## Module versions

- Server Runtime: **2.3.52**
- Web Chat: **1.4.47**
- LALM Engine: **2.1.26**
- LALM UI: unchanged
- Google Account architecture: unchanged

## Trigger / evidence

The latest whole-conversation camera log showed two remaining issues after the intent-gate correction:

1. A social response could stream a standalone `§wyrlz` line before the rest of the answer and only become visually cleaned after completion.
2. The next turn in the same conversation still reported `cached 0` and rebuilt the entire prompt, even though the prior assistant turn had already completed on the same worker.

The first completed social response also lacked a published response-state checkpoint in its completion receipt, which pointed at the generated-text re-tokenization guard as the cache break.

## Changes

### Web Chat 1.4.47

`web/chat_background_resume.js` now buffers only a possible leading assistant-name fragment. If the stream resolves to a standalone `§wyrlz` line followed by a newline, that line is suppressed before it ever reaches the visible message state. If the text instead becomes a natural sentence such as `§wyrlz is ...`, the buffered text is released unchanged.

This applies to normal live streaming and background/replay paths without delaying unrelated first tokens.

### LALM Engine 2.1.26

`runtime_hot/r39_engine.py` no longer reconstructs generated checkpoint keys by decoding assistant text and re-tokenizing it. The recurrent state already corresponds to the exact sampled token IDs, so assistant-open checkpoints are now keyed directly from:

`prompt token ids + sampled generated token ids`

The speculative next-turn warmup then advances that exact state through the assistant close marker and next user-open scaffold as independently encoded special-token suffixes. This removes false cache misses caused by an equivalent decoded string re-encoding to a different BPE sequence.

New capability receipts:

- `tokenExactGeneratedCheckpoints=true`
- `nextTurnBoundaryCheckpointing=true`

## Expected observable behavior

For a continuing conversation on the same live worker, the next response should report a checkpoint hit and a nonzero reused-token count, with only the new user suffix requiring prefill.

A new Vercel worker still cannot reuse another worker's in-memory recurrent state; cross-instance durable prefill state remains a separate future architecture item.
