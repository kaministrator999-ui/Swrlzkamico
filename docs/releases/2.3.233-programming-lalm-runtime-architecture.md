## Goal

Preserve the architecture curriculum as §wyrlz's internal programming operating grammar, apply the same principles proportionally when §wyrlz designs user projects, and define the implementation path from documentation to executable coding behavior without creating a second competing cognitive authority.

## Architecture decision

Use one primary §wyrlz LALM as the authority for user intent, conversation/context, project architecture, constraints, coding-plan ownership, acceptance, and user-facing explanation.

Implement programming specialization in the same LALM first through:

- coding-task routing;
- programming context compilation;
- architecture-reconciliation state;
- programming obligation tracking;
- repository/tool planning through server authority;
- architecture-aware completion/acceptance evaluation.

A dedicated coding model may be introduced later only as a subordinate specialist/proposal engine. It may generate patches/tests/refactor alternatives, but it must not independently own project truth, architecture policy, deployment authority, version authority, or final acceptance.

## Capability truth ladder

Programming/model capability must be described using distinct states:

1. documented;
2. runtime scaffolded;
3. tool-integrated;
4. deterministically evaluated;
5. live verified;
6. learned/trained.

Do not collapse documentation into implementation or implementation into training.

## Implementation plan

- Phase 0 — curriculum/governance foundation: substantially established.
- Phase 1 — same-LALM programming mode/context compiler.
- Phase 2 — programming obligations + architecture acceptance.
- Phase 3 — repository/tool execution loop.
- Phase 4 — runtime user-project architecture adaptation/coaching.
- Phase 5 — optional coder specialist, only after benchmarks justify it.
- Phase 6 — training/fine-tuning, only after generalized evaluation data exists.

## User-project behavior

The same underlying architecture grammar should guide projects built with §wyrlz, but proportionally. Tiny projects stay lightweight. Persistence, multiple users, deployment, automation, external APIs, AI/agents, or long-lived maintenance justify progressively stronger state ownership, contracts, tests, logging, versioning, migrations, and deployment boundaries.

The user may reject optional architectural preferences. §wyrlz should explain meaningful tradeoffs and simplify coherently rather than forcing internal §wyrlz repository architecture onto another project.
