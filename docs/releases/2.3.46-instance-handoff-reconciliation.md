# Server Runtime v2.3.46 — Instance handoff reconciliation

## Module state

- Server Runtime: **v2.3.46**
- Web Chat: **v1.4.41**
- LALM Engine: **v2.1.25** (unchanged)

## Goal

Make a pending Chat response recover cleanly when the hosting worker changes while §wyrlz is still prefilling or generating.

## What changed

- The background-resume bridge now records the originating server instance when possible and compares it with the instance observed when Chat returns.
- Reattachment still starts immediately with the same request id and original request body; it does not wait for the instance comparison before resuming work.
- If the original detached job still exists, its replayed stream is reconciled against the partial assistant text already stored in Chat and only unseen output becomes visible.
- If the worker changed and the in-memory job disappeared, posting the same request id causes the replacement worker to begin the request again immediately.
- The resumed stream is compared character-for-character with the partial response already displayed. Matching regenerated text is hidden while it catches up, then normal continuation becomes visible once it passes the saved boundary.
- If the replacement generation diverges before reaching the saved boundary, Chat switches to a clean redo and replaces the old partial text with the regenerated stream rather than stitching incompatible output together.
- Resume contexts now include the request id, thread id, stream sequence cursor, timer, terminal state, and reconciliation state expected by the normal stream consumer.
- A resumed stream ending without a terminal event is treated as recoverable and retried instead of being silently accepted as finished.
- Recovery retry delay was shortened and foreground/page-show recovery starts sooner so instance handoff feels immediate.

## Existing server/LALM behavior used

- R39 jobs are detached from the browser connection and keyed by request id on the active worker.
- A repeated request id on the same worker replays the existing job event history and follows new events.
- A repeated request id on a replacement worker creates a new detached job when the former worker-memory job no longer exists.
- The LALM engine itself was not changed in this release.

## Important durability boundary

The server still stores detached job history in worker memory. v2.3.46 makes worker replacement recoverable from the browser by automatically restarting and reconciling the request, but it does not create a cross-worker durable inference checkpoint. A future durable job/event store would allow a replacement worker to continue from the exact server-side compute checkpoint instead of regenerating from the beginning.
